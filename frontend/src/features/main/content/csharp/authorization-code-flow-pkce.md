# Authorization Code Flow with PKCE

## Summary

Authorization Code Flow with Proof Key for Code Exchange (PKCE) is an OAuth 2.0 flow used to securely obtain tokens for public clients such as SPAs, mobile apps, and desktop apps.

## What It Is

Public clients cannot safely store a client secret.

PKCE solves this by adding a temporary secret pair:

- code_verifier: random high-entropy string generated by the client
- code_challenge: hash of code_verifier sent in authorization request

Later, during token exchange, the client must send the original code_verifier.
The authorization server verifies it matches the earlier code_challenge.

## Why It Is Current Best Practice

- Prevents authorization code interception and replay attacks.
- Removes dependency on static client secrets in public clients.
- Recommended by OAuth 2.0 Security Best Current Practice.
- Required or strongly encouraged by major identity providers.

## How It Works (Step by Step)

### Step 1: Generate Code Verifier and Code Challenge

```csharp
using System.Security.Cryptography;
using System.Text;

static string Base64UrlEncode(byte[] bytes) =>
    Convert.ToBase64String(bytes)
        .Replace("+", "-")
        .Replace("/", "_")
        .TrimEnd('=');

static string GenerateCodeVerifier()
{
    var bytes = RandomNumberGenerator.GetBytes(64);
    return Base64UrlEncode(bytes);
}

static string CreateCodeChallenge(string codeVerifier)
{
    var hash = SHA256.HashData(Encoding.ASCII.GetBytes(codeVerifier));
    return Base64UrlEncode(hash);
}

string codeVerifier = GenerateCodeVerifier();
string codeChallenge = CreateCodeChallenge(codeVerifier);
```

### Step 2: Redirect User to Authorization Endpoint

```text
GET https://authorization-server.com/auth?
  response_type=code&
  client_id=your_client_id&
  redirect_uri=https://yourapp.com/callback&
  scope=openid profile email&
  code_challenge=codeChallenge&
  code_challenge_method=S256
```

Important fields:

- code_challenge: hashed verifier
- code_challenge_method: usually S256

### Step 3: User Authenticates and Grants Consent

The user signs in and approves requested scopes.
The authorization server redirects to your callback URL with an authorization code.

### Step 4: Exchange Authorization Code for Tokens

```text
POST https://authorization-server.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&
code=authorization_code_received&
redirect_uri=https://yourapp.com/callback&
client_id=your_client_id&
code_verifier=codeVerifier
```

The server validates that:

- SHA256(code_verifier) matches the earlier code_challenge
- authorization code is valid and not reused

### Step 5: Receive Tokens

If validation succeeds, server returns access token and optionally ID token/refresh token.
The client uses access token to call protected APIs.

## Why PKCE Protects Better

Without PKCE, if an attacker steals the authorization code, they might exchange it for tokens.

With PKCE, stolen code alone is not enough, because attacker also needs the original code_verifier.

## Common Implementation Tips

- Always use S256 challenge method.
- Store code_verifier only for the short auth round-trip.
- Validate state parameter to prevent CSRF.
- Use HTTPS for all redirect and token endpoints.

## Real-World Analogy

Think of authorization code as a luggage claim ticket.

PKCE adds a second proof: a private matching number only the real owner has.
Even if someone steals the ticket, they cannot collect the luggage without that second proof.
